# 开发流程

> 目标读者：参与开发或接手本项目的开发者（或 AI）。
> 架构细节见 [`架构.md`](架构.md)，关卡编写规范见 [`关卡编写规范.md`](关卡编写规范.md)。

---

## 1. 环境要求

| 依赖 | 最低版本 | 用途 |
|------|---------|------|
| Rust | **1.75+**（开发机 1.94） | 核心引擎 crates、`regzero-wasm`、`regzero-bridge` |
| Node.js | **≥ 18**（开发机 24） | `web/` 前端（React + Tailwind + CodeMirror 6）开发与构建 |
| `wasm-pack` | 最新稳定版 | 将 `crates/regzero-wasm` 编译为前端可加载的 WASM 包 |
| 本地 C 工具链 | `gcc` 或 `clang` | 第 3~6 章本地 C 项目编译与参考编译器端到端自检（Windows 推荐 MSYS2 MinGW-w64；`regzero-bridge` 启动时自动体检） |
| GNU Make | 任意 | 统一构建与测试命令入口 |

> **离线构建说明**：根目录 `.cargo/config.toml` 默认配置 `[net] offline = true`，防止多个 `cargo` 进程同时更新 crates.io 索引导致假死锁。引入新依赖（如 `axum`、`wasm-bindgen`、`notify`）时，先单独联网缓存一次，再恢复离线模式。

## 2. 日常开发启动方式

### 2.1 核心引擎与关卡自检（当前立即可用）

```bash
# 全工作区 Rust 单元测试 + 关卡自检
cargo test --workspace

# 单独测试某个核心 crate（反馈最快）
cargo test -p riscv-simulator
cargo test -p riscv-assembler
cargo test -p starlang
cargo test -p regzero-core
```

### 2.2 网页前端 + WASM + 本地桥接联调（迁移落地后）

```bash
# 1. 编译浏览器 WASM 引擎到 web/src/wasm-pkg/
wasm-pack build crates/regzero-wasm --target web --out-dir ../../web/src/wasm-pkg

# 2. 启动现代 Web 前端（Vite HMR 毫秒级热更新）
cd web && npm install && npm run dev

# 3. 启动本地桥接服务：
#    3a) 绑定第 3~6 章本地 C 工程
cargo run -p regzero-bridge -- --project ./content/templates/chapter3-starter
#    3b) 绑定第 1~2 章本地单文件监听
cargo run -p regzero-bridge -- --watch-file ./my_level1_5.s
#    3c) 本地一体托管（同时提供静态前端页面，访问 http://127.0.0.1:17320）
cargo run -p regzero-bridge -- --serve-web ./web/dist --project ./my-compiler
```

## 3. 关卡自检（不可绕过的质量守门人）

修改任何关卡、测例或引擎代码后，必须运行以下自检：

```powershell
# 全量关卡自检（用参考解跑通所有关卡测例）
cargo test -p regzero-core selfcheck -- --nocapture

# 只自检指定关卡（开发单关时最省时间）
$env:NMC_SELFCHECK="1-5,1-6"; cargo test -p regzero-core selfcheck_only -- --nocapture

# 逐条测例打印 输入 / 期望 / 实际（默认汇总只报第一条失败，排错必用 verbose）
$env:NMC_SELFCHECK="1-5"; $env:NMC_SELFCHECK_VERBOSE="1"; cargo test -p regzero-core selfcheck_verbose -- --nocapture

# 关卡配置与编辑器约束一致性检查（抓只读行越界、提示行号错误等自检抓不住的问题）
cargo test -p regzero-core every_level_page_and_test_config_are_consistent
```

bash 下将 `$env:VAR="val";` 改为前置 `VAR=val ` 即可。

## 4. 新增或重构一个关卡的标准动作

1. 在 `content/levels/cN_M/` 下创建或更新 `meta.json`、`lesson.md`、`tests.json`、初始代码（若为第 1~2 章）与参考解。
2. 补齐 `meta.json` 中的 `goalSummary`、`sandbox` 强交互配置与 3 级 `hints`。
3. 跑单关自检 + 一致性检查，确保全绿。
4. 在浏览器打开 `/level/N-M` 人工走一遍完整闭环：**看懂目标 → 玩通热身沙盘 → 故意写错看 Diff 与一键调试 → 写对看通关反馈**。

## 5. Windows 编码与 Git 提交纪律（血泪教训）

1. **严禁使用 PowerShell `Set-Content` / `Out-File` 写含中文的文件**：它们默认按 GBK 写入，会不可逆破坏 UTF-8 源码。统一使用编辑器或明确 UTF-8 写入的工具。
2. **不要被控制台乱码误导**：PowerShell 显示中文乱码不代表文件本身损坏，确认编码以编辑器或 UTF-8 读取为准。
3. **Makefile 中的 Windows 命令**：在 MSYS2 sh 环境下调用 Node 工具需保留 `.cmd`（如 `npx.cmd`、`npm.cmd`），且 `echo` 中不要放中文。
4. **提交前必检 `git status --short`**：严防探针文件、临时 `CARGO_TARGET_DIR` 或测试残件混入提交。
5. **分支纪律**：主开发分支为 **`main`**；中文提交信息建议写入临时 UTF-8 文件后用 `git -c i18n.commitEncoding=UTF-8 commit -F <file>` 提交。
6. **避免多进程争抢 `target/` 锁**：并行执行测试时如遇 `Blocking waiting for file lock`，等待重试即可，不要随意另建未清理的 `CARGO_TARGET_DIR`。
